## 1. 출발점

입력 문서는 `idea_md/공매물건-지도검색-MVP-개발계획서-v0.3.md`였다.
Core / MCP / Web 3계층을 제안하고 M0~M9 마일스톤과 MCP 툴 4종을 정의한 문서다.

요청은 **"1차적으로 MCP를 만들고 싶은데 정의해야 할 부분을 토론하자"** 였다.

여기서 첫 논점이 나왔다. 계획서에서 MCP(M5.5)는 **이미 만들어진 SQLite 인덱스를 감싸는 얇은 층**이라,
M1~M5가 끝나 있어야 성립한다. "MCP를 먼저 만든다"는 건 그 전제를 깨는 것이었다.

**해법: 계약 우선(contract-first)**

> MCP 툴 4종의 입출력 계약을 **먼저 문서로 확정**하고, DB 스키마와 store 쿼리를 그 계약에서 **역산**한다.

이러면 "MCP를 1차로 정의"하는 게 되면서 구현 순서는 계획서를 그대로 지킬 수 있다.
이 원칙이 이후 모든 작업의 뼈대가 되었다 (SPEC §1.5②).

## 3. 확정된 의사결정

### 3.1 구조·범위

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 착수 순서 | 구현은 계획서대로 M1~M5 → MCP. 단 **계약을 먼저 확정** | 계약 없이 파이프라인을 만들면 마지막에 필드 부족이 드러나 스키마를 거슬러 수정해야 함 |
| 2 | 저장소 | `onbid-mcp/` 단독. 내부에 `core/` + `onbid_mcp/`. Web은 Phase 2 별도 저장소 | `core`를 import 가능한 패키지로 유지하면 분리 비용이 0 |
| 3 | 의존 방향 | `mcp → core` 단방향. MCP는 HTTP를 거치지 않고 `core` 직접 호출 | 불필요한 HTTP 홉은 프로세스 관리와 실패 모드만 늘림 |
| 4 | 온비드 API 계열 | **차세대 계열로 통일** (`151572xx`), 레거시(`150008xx`) 미사용 | 차세대에 부동산 물건목록이 존재함을 확인 → 혼용할 이유 없음 |

### 3.3 MCP 인터페이스

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 9 | 파라미터 어휘 | 코드값·한글 명칭 **둘 다 수용**, 값 모양으로 자동 판별 | LLM 왕복 감소. 단 `region`은 온비드에 코드가 없어 **명칭 전용** |
| 10 | 코드표 노출 | 툴이 아니라 **MCP Resource** | 툴로 만들면 매 검색마다 왕복 1회 추가. 툴 표면을 넓히지 않음 |
| 11 | 정렬 | 사용자 지정 `sort`는 화이트리스트로 허용, **기본은 마감일 오름차순** | 기본을 "최저가율 낮은 순"으로 두면 서비스가 순위를 매기는 것 = 랭킹 금지 위반 |

| 14 | 오류 규약 | `no_result`를 **빈 배열로 반환하지 않음** | 빈 배열은 "없다"와 "실패했다"를 구분 못 해 LLM이 잘못된 결론을 냄 |

### 3.5 적재 아키텍처 (2026-08-19 변경)

**SQLite → Supabase(PostgreSQL)**. 사용자 요청이며, Phase 2 Web과 단일 진실원천을 공유하고
Mac·Windows 교차 작업에서 데이터가 갈라지지 않게 하는 것이 목적이다.

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 20 | Supabase 프로젝트 | **기존 공유 프로젝트 + RLS anon 전면 차단** | 무료 티어 프로젝트 수 제한 회피. Phase 1은 개인용 MCP라 anon 읽기가 아예 필요 없음 |
| 21 | 접속 방식 | **psycopg 직접 연결** (`krx-signal-alerts` 전례) | 6천여 건 배치 upsert. PostgREST의 1000행 상한·`ON CONFLICT` 제약을 받지 않음 |
| 22 | 조회 경로 | **전부 원격.** 지오코딩 캐시도 Supabase에 보관 | 단일 진실원천이 가장 단순. 두 개발 환경이 캐시를 공유해 카카오 호출 중복 제거 |

**착수 전 확인한 사실**: `krx-stock-charts`·`krx-signal-alerts`·`utube-trend-tracer` 세 프로젝트가
**같은 Supabase 프로젝트를 공유**한다(URL 해시 동일). anon 키는 테이블이 아니라 **프로젝트 단위**로
발급되므로, 아무 조치 없이 테이블을 추가하면 기존 웹앱 3개의 anon 키로 공매 데이터가 조회된다.
테이블 접두어(`onbid_`)는 이름 구분일 뿐 권한 분리가 아니다.

이는 보안 문제인 동시에 **법적 문제**다 — 공매 물건이 무제한 조회되면 SPEC §2.4의 "게시형 표시·광고 금지"
경계를 넘어 사실상 카탈로그가 된다. 그래서 §6.6에 규칙 R1~R6을 두고, **테이블 생성과 RLS 차단을
같은 마이그레이션에서 처리**하며 **anon 키로 실제 차단을 실측 확인**(AC12)하도록 M3에 배치했다.

## 4. 계획서 v0.3에서 발견한 문제

토론과 문서 작업 중 **계획서 자체의 오류·누락**이 여러 건 나왔다.

| # | 문제 | 조치 |
|---|---|---|
| 1 | **`get_auction_stats`가 낙찰가율을 반환한다고 했으나, 진행 중 물건만 수집하므로 산출 불가** | 통계 범위 축소, 낙찰가율 Phase 2 이월 |
| 2 | 사라진 물건 처리 방침이 없어 이력·알림이 성립하지 않음 | tombstone 도입 |
| 3 | `search_auction_items` 입력에 **최저가율 구간이 빠져 있음** — 핵심 가치 가설 검증 수단이 없음 | `min_rate`/`max_rate` 추가 |
| 4 | 코드 조회 경로가 없어 LLM이 검색을 시작조차 못 함 | Resource 3종 + 명칭 수용 |
| 5 | **처분방식(매각/임대) 축 자체가 없음** — 임대 물건이 섞임 | `dspsMthodCd=0001` 필터 추가 |
| 6 | 재산유형 축이 없음 | `prptDivCd` 필터·집계 축 추가 |
| 7 | PK를 단일 `cltr_no`로 가정 — 실제로는 복합키 | `(cltr_mng_no, pbct_cdtn_no)`로 변경 |

이 외에 활용가이드·실측으로 확정한 사항까지 합쳐 **SPEC 부록 A에 변경 이력 37건**을 남겼다.

## 5. 실측으로 뒤집힌 전제 (2026-08-19)

M1 첫 작업으로 **실호출 스모크**를 배치한 것이 결정적이었다. 문서만으로는 알 수 없던 사실이 나왔다.

| # | 문서상 전제 | 실측 결과 | 영향 |
|---|---|---|---|
| 1 | 온비드가 최저가율(`apslPrcCtrsLowstBidRto`)을 제공 | **채움률 0%** — 전수 6,161건에서 하나도 오지 않음 | 자체 계산으로 전환 (가능률 95.0%). SPEC 변경 #24를 #30으로 철회 |
| 2 | PNU 제공으로 지오코딩 부담 급감 | 지번PNU **결측 28.9%**, 도로명PNU **36.2%** | PNU는 지오코딩을 대체하지 못함. 단 읍면동 결측 0%라 폴백은 항상 성립 |
| 3 | 오퍼레이션명 `getRlstCltrList` | **`getRlstCltrList2`** — 가이드 본문이 오류 | 실호출 없이 구현했다면 M1 전체가 막혔을 것 |
| 4 | 오류는 `{"header":{"resultCode":...}}` 한 형식 | **게이트웨이 오류는 다른 봉투 + HTTP 400** | 파서가 두 봉투를 모두 처리해야 함 |
| 5 | 코드표로 명칭 변환 가능 | `bidDivCd=0001`이 코드표는 "인터넷", 응답은 **"전자입찰"** | 표시 명칭은 응답 `*Nm` 필드 사용 |
| 6 | 입찰일시는 정상 날짜 | **`2999...` sentinel** 0.3% (일정 미정) | 정렬·필터 오염 방지 규약 신설 |
| 7 | 페이지 순회로 트래픽 우려 | **`numOfRows=5000` 동작 → 전량 3~4콜** | 트래픽 우려 해소. 병목이 수집 → 지오코딩으로 이동 |

> **교훈**: 활용가이드는 신뢰할 수 있는 1차 자료가 아니었다.
> 그래서 `API_FINDINGS.md`를 만들고 **충돌 시 실측이 가이드보다 우선**하도록 명시했다.
